# Stage 3 (end): Audit and verification report

Prove what was built against the approved spec, honestly (a spike has no spec: its Gate 3 is in `light.md`). Output: the audit run in `app/audits/runs/`, `ideas/<slug>/verification.md`, `ideas/<slug>/outcome.md`. Ends at **Gate 3**.

## Steps
1. **Spec conformance audit** (`factory/audits/spec-conformance.md`), as written, against `spec/` (the spec is supplied; never reconstruct one). Every item gets one of the five outcomes: verified, partially verified, not verified, failed, not applicable. Include the composition check (each component and version in `composition.json` against the code) and tests expected (doc 11) against tests run.
2. **Independent tests** (tiers 2 and 3; `factory/standards/testing.md`): a fresh context (a subagent or a new session) that has not seen the build's tests or code is given the spec pack and how to reach the app from outside (its API, CLI or UI, from the README), and writes tests for every PERM (an allowed role and a refused one), every RULE example, and the negative and edge ACs of each Must FR. Run them in the clean container. Each failure is a finding (step 3); a test that is itself wrong is fixed against the spec, never against the code. Those that pass are kept in the app's suite, marked as independent (in a folder or with a tag the stack allows). Record written, passed and failed in `verification.md`.
3. Apply the findings discipline in `factory/audits/LOG_PROTOCOL.md`: verify each finding before it counts, tag it Important, Nit or Pre-existing, and answer every one (fixed, or closed with a reason). Fix failed items that the spec requires and re-run (delta only, three rounds at most, then reconsider the approach with the owner) until none remain, or record each one left with the owner's decision. Open Important findings block Gate 3.
4. **Other audits** (`factory/audits/README.md`): refactor and hardening is required at tier 3, recommended for a prototype that holds Confidential or personal data, and before publishing anything public (for an AI feature it includes prompt injection and tool misuse); UI polish after UI work; data integrity when the data matters. Offer them at the gate; run when asked.
5. **Verification report** (`verification.md`, `factory/standards/testing.md`): commands and suites run; environment and versions; pass/fail/skip counts; the independent tests' counts, separately; for an AI feature, the eval results (`factory/standards/ai-features.md`: model ID, prompt versions, set size, pass rate against the threshold, cost); tests **not run** and why; static and security checks; known failures and defects; conformance gaps; manual checks still needed; whether the app started clean; whether integrations were exercised or mocked; the recommended next action. Passing tests are evidence, not proof. Update `state.json` `last_verification`.
6. **Lessons and reuse:** candidate reusable assets and lessons from this build (factory spec 9.6). Each goes through the catalogue's validation and approval later; none becomes trusted by being proposed. Learned choices go into `learned.md` (`learned.py add`).
7. **Outcome** (`outcome.md`): did the Gate 1 assessment hold? `python factory/scripts/learned.py outcome <slug>` writes it with the ratings, the effort and the one thing approved at Gate 1. Fill in, from the build and the audit: for each foundation whether its rating `held` (`yes`, `partly`, `no`) and what showed it; the actual person-weeks; whether the one thing was the thing that mattered; and the `lessons` for the factory, each naming the lens, knock-out rule, default or RICE factor it would change (none is a valid answer). Be honest rather than kind: an outcome that always says `yes` teaches nothing. `python factory/scripts/learned.py check <slug>` must pass.
8. Write `gates/gate-3.md`, set `state.json`, stop.

## Gate 3 shows
**Done:** what was built and how to run it. **Results exactly as run** (each run or not run). **Audit:** the confirmed-Important count first ("0 findings" if none); counts by outcome; failed and not-verified items first; findings not confirmed and pre-existing ones listed separately; rounds taken; the independent tests written, passed and failed. **Outcome:** the foundations that did not hold, effort estimated against actual, the lessons. **Recommended:** readiness, and whether to run more audits. **Decisions for you:** deferred items, accepted limitations, reuse candidates, and any candidate change from `learned.py review`. **Risks.** **Next:** Publish.
