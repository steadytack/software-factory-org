# Stage 2: Spec and solution composition

Turn the approved Application Definition into a portable spec pack and a feasible composition. Output: `ideas/<slug>/spec/`, `ideas/<slug>/composition.json`. Ends at **Gate 2**.

## Before you start
Gate 1 is approved (`state.json`). Read the definition, `decisions.md`, and the standards `specification-pack.md` and `requirement-ids.md`.

## Steps
1. `python factory/scripts/scaffold.py spec <slug>` writes the stubs (README index and 01-12), filled from the definition.
2. **Questions** (round 2 at most, if round 1 was at Gate 1): only gaps, conflicts and open items, with recommendations; list the rest as answered from defaults or the source. Record every answer in `decisions.md`; an answer that differs from the recommendation also goes into `factory/context/learned.md` (status `observed`, with its scope).
3. **Write the pack.** Specific, testable, one requirement per row; no technology in requirements; proportionate to the tier (`Not applicable: reason` is allowed, padding is not). Every item has a source (a question, the definition, a default, the source document, or an assumption).
4. **Catalogue discovery and composition (doc 12).** For each required capability (CAP): search the catalogue across all asset types; rank candidates by fit (not name); record the selected asset and version, and one decision: **reuse**, **adapt**, **build**, **import** (bring in a candidate for assessment), **redesign** (change the solution to use an existing capability) or **defer**. Do not force reuse of an asset that is insecure, incompatible or unsuitable. For a gap, explain why candidates fall short, recommend an option with its complexity, and put approved build work into the delivery plan; mark reuse scope `catalogue` when the new work should become an asset after validation.
5. **Composition manifest.** `composition.json` (schema `factory/schemas/composition.schema.json`): components with their base and modules as catalogue IDs and versions, links between components, configuration names (never secret values), adaptations, validation status `not-run` until Build proves it, known limitations. A single-template app has one component. Composition across templates is limited to what the factory has proven; say so rather than presenting an unproven combination as working.
6. **Architecture (doc 10)** agrees with the composition: every component (CMP) is built from a CAT asset, custom code, or an external component (a third-party service not yet in the catalogue: a warning until it is imported and approved); every interface between components is an INT.
7. **Delivery plan (doc 11).** Epics in order (one epic for a small app), each independently testable with its stories, components and dependencies; tests (TEST) naming what they verify; Definition of Done; release acceptance.
8. **Import mode** (an imported source exists): `spec/source-map.md` has a row for every source ID, Mapped (to the spec IDs it became) or Deferred (with a reason); keep the source's wording where clear.
9. **Check:** `python factory/scripts/check_spec.py <slug>` until it reports **no blockers**; it writes `spec/traceability.md`. Warnings are listed at the gate, each fixed or accepted.
10. Write `gates/gate-2.md` with the Definition of Done below, set `state.json`, stop at Gate 2.

## What check_spec.py enforces
Blockers: a missing document; a duplicate ID; a mention of an ID that is not defined; a broken relative link; no FR; an FR without a priority, without a journey or objective, without a story or without an epic (Could: warnings); a story without an FR or an acceptance criterion; an AC without a verification (tier 1: warning); a RULE, SCR, DATA, PERM or INT naming no FR; a PERM with no role; a component not built from a catalogue asset, custom code or an external component; an epic delivering nothing; a capability with no decision, no requirement (unless infrastructure), or a build/import/redesign/defer without a rationale; reuse or adapt without a selected asset; a selected asset that is missing, not approved, deprecated or archived; an open ASM, Q, RISK or DEP that blocks the spec; an imported source ID neither mapped nor deferred; an invalid Application Definition.
Warnings: metadata table missing; placeholder text; journeys without requirements; objectives without a success measure; NFR or SEC without verification; NFR without a threshold; permission without a test; open item without an owner; references to withdrawn items; a catalogue version that differs; an external component not yet in the catalogue; deployment in doc 10 differing from the definition.

## Gate 2: Definition of Done (factory spec section 28)
The definition is approved; users, outcomes and scope are clear; tier, deployment and interfaces recorded; design decisions recorded; requirements testable for the tier; NFRs defined; screens and journeys documented where applicable; data model at the right level; security and privacy addressed proportionately; stories have acceptance criteria; assumptions, risks, decisions and questions recorded; catalogue discovery done; doc 12 complete; `composition.json` created (or marked not applicable); compatibility and licence recorded as far as verified; every gap has a decision; architecture consistent with the composition; the plan has epics, stories, dependencies and release boundaries; traceability holds; `check_spec.py` has no blockers (or the owner accepted an exception explicitly); the pack has its index and version. Mark each item done, or not applicable with why.

Gate 2 shows: **Done** (the pack, the counts from `traceability.md`, the check result exactly as run), **Recommended** (first release, build order, the composition), **Decisions for you** (open questions, riskiest assumptions, gap decisions), **Risks**, **Next** (Build).
