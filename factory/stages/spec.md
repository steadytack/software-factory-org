# Stage 2: Spec and solution composition

Choose the shape of the solution, then turn it into a portable spec pack and a feasible composition. Output: `ideas/<slug>/application-definition.md` (the solution choices), `ideas/<slug>/spec/`, `ideas/<slug>/composition.json`. Ends at **Gate 2**, which approves the solution choices and the spec together.

## Before you start
Gate 1 is approved with **Go** (`state.json`). Read the idea brief, the assessment (the ambers and the one thing become risks and assumptions here), `overview.md`, `decisions.md`, and the standards `specification-pack.md` and `requirement-ids.md`.

## Solution choices
The choices that shape everything after them are made first, in `application-definition.md`. It stays a document of its own (rather than being folded into spec docs 01, 02 and 10) because it is one small machine-readable record (`factory/schemas/application-definition.schema.json`) that the spec stubs, `check_spec.py` (tier and deployment) and the status page read; problem, outcome, users and success measures are not repeated in it: they are in the brief.
1. `python factory/scripts/scaffold.py definition <slug>` writes it; fill it in. Every choice in the JSON block is `recommended` (with `reason`, and `default` when a DEF-nn answered it) until the owner answers at Gate 2.
2. **Lenses.** Activate the relevant lenses (`context/lenses/README.md`); record active and skipped (with reasons).
3. **Maturity tier** (1 Explore, 2 Personal tool, 3 Shared pilot, 4 Operational; default DEF-01). The tier sets the depth of testing, security and documentation, not the deployment. A low tier never overrides a clear security or privacy need.
4. **Deployment category**: simple/self-contained (no Docker just for consistency), local (Docker Compose, the default when a server is needed), hosted/shared, automated/background. State the development environment when it differs.
5. **Interfaces** (combinable): web, mobile, specialist visual (map, timeline, chart, editor), conversational, non-visual (API, CLI, job, agent). **Design:** brand, design system and interaction style; infer the visual direction from them, and ask only if it is materially ambiguous.
6. **Template and catalogue.** Compare the idea with the template table below and search the catalogue (`python factory/scripts/catalogue.py search <terms> --scope <scope>`). Recommend one template, or **none fits**, with why, the runner-up and what it does not cover. List candidate assets (`candidate_assets`) with their fit and limitations, and the initial composition hypothesis. Only `approved` assets are reused (POL-10). Confirmed reference cards (systems, processes, policies) are not reused: they say what already exists, so the idea integrates with them, follows them, or says why it duplicates them; read the card's source link when the idea touches it, and flag a stale card.
7. **Data, identity, integrations, security, operations:** what is stored and how sensitive it is (the data classes from the assessment), who logs in, outside systems (`system-landscape.md`), what could go wrong, how it is run and backed up.

## Steps
1. `python factory/scripts/scaffold.py spec <slug>` writes the stubs (README index and 01-13), filled from the definition.
2. **Questions** (one round in this stage, DEF-17): the solution choices that are materially open, then gaps, conflicts and open items in the spec, each with a recommendation; list the rest as answered from defaults or the source. Only questions whose answer changes architecture, cost, risk, usability or delivery (`context/lenses/README.md`). Record every answer in `decisions.md`; an answer that differs from the recommendation also goes into `factory/context/learned.md` (status `observed`, with its scope).
3. **Write the pack.** Specific, testable, one requirement per row; no technology in requirements; proportionate to the tier (`Not applicable: reason` is allowed, padding is not). Every item has a source (a question, the brief, the definition, a default, the source document, or an assumption). The brief's assumptions and unknowns, the assessment's ambers and the one thing become ASM, RISK and Q in doc 09.
4. **Catalogue discovery and composition (doc 12).** For each required capability (CAP): search the catalogue across all asset types; rank candidates by fit (not name); record the selected asset and version, and one decision: **reuse**, **adapt**, **build**, **import** (bring in a candidate for assessment), **redesign** (change the solution to use an existing capability) or **defer**. Do not force reuse of an asset that is insecure, incompatible or unsuitable. For a gap, explain why candidates fall short, recommend an option with its complexity, and put approved build work into the delivery plan; mark reuse scope `catalogue` when the new work should become an asset after validation.
5. **Composition manifest.** `composition.json` (schema `factory/schemas/composition.schema.json`): components with their base and modules as catalogue IDs and versions, links between components, configuration names (never secret values), adaptations, validation status `not-run` until Build proves it, known limitations. A single-template app has one component. Composition across templates is limited to what the factory has proven; say so rather than presenting an unproven combination as working.
6. **Architecture (doc 10)** agrees with the composition: every component (CMP) is built from a CAT asset, custom code, or an external component (a third-party service not yet in the catalogue: a warning until it is imported and approved); every interface between components is an INT.
7. **Business process (doc 13).** The as-is process (who does what today, hand-offs, waits, rework; start from the brief's "How it's done today") and the to-be process with the app, each as a Mermaid flowchart in a ```mermaid block. Under the to-be flowchart, a steps table (Step, Who, What happens, Relies on) naming the FRs each step relies on; a step the app does not support says so. Then a **What changes** table: each step removed, automated, changed or new, who does it before and after, and the expected time or error saving. Write it after the FRs, so every reference resolves; an FR that no to-be step needs is worth questioning.
8. **Delivery plan (doc 11).** Epics in order (one epic for a small app), each independently testable with its stories, components and dependencies; tests (TEST) naming what they verify; Definition of Done; release acceptance.
9. **Import mode** (an imported source exists): `spec/source-map.md` has a row for every source ID, Mapped (to the spec IDs it became) or Deferred (with a reason); keep the source's wording where clear. Record the source in the definition's `sources`.
10. **Check:** `python factory/scripts/check_spec.py <slug>` until it reports **no blockers**; it checks the definition and the pack, and writes `spec/traceability.md`. Warnings are listed at the gate, each fixed or accepted.
11. Write `gates/gate-2.md` with the Definition of Done below, set `state.json`, stop at Gate 2.

## What check_spec.py enforces
Blockers: a missing or invalid Application Definition; a missing document; a duplicate ID; a mention of an ID that is not defined; a broken relative link; no FR; an FR without a priority, without a journey or objective, without a story or without an epic (Could: warnings); a story without an FR or an acceptance criterion; an AC without a verification (tier 1: warning); a RULE, SCR, DATA, PERM or INT naming no FR; a PERM with no role; a component not built from a catalogue asset, custom code or an external component; an epic delivering nothing; a capability with no decision, no requirement (unless infrastructure), or a build/import/redesign/defer without a rationale; reuse or adapt without a selected asset; a selected asset that is missing, not approved, deprecated or archived; an open ASM, Q, RISK or DEP that blocks the spec; an imported source ID neither mapped nor deferred; doc 13 without an as-is or a to-be section, or either without a ```mermaid block.
Warnings: an unresolved solution choice; metadata table missing; placeholder text; journeys without requirements; objectives without a success measure; NFR or SEC without verification; NFR without a threshold; permission without a test; open item without an owner; references to withdrawn items; a catalogue version that differs; an external component not yet in the catalogue; deployment in doc 10 differing from the definition; a to-be step (doc 13) naming no FR; doc 13 with no to-be steps table or no What changes table.

## Gate 2: Definition of Done (factory spec section 28)
Gate 1 is approved with Go; the solution choices are recorded (tier, deployment, interfaces, design, template and runner-up, candidate assets, lenses); users, outcomes and scope are clear; requirements testable for the tier; NFRs defined; screens and journeys documented where applicable; the as-is and to-be business process and what changes (doc 13); data model at the right level; security and privacy addressed proportionately; stories have acceptance criteria; assumptions, risks, decisions and questions recorded (the assessment's ambers and one thing among them); catalogue discovery done; doc 12 complete; `composition.json` created (or marked not applicable); compatibility and licence recorded as far as verified; every gap has a decision; architecture consistent with the composition; the plan has epics, stories, dependencies and release boundaries; traceability holds; `check_spec.py` has no blockers (or the owner accepted an exception explicitly); the pack has its index and version. Mark each item done, or not applicable with why.

Gate 2 shows: **Done** (the solution choices, the pack, the to-be process from doc 13 in a sentence or two, the counts from `traceability.md`, the check result exactly as run), **Recommended** (tier, deployment, interfaces, design, template and runner-up, the composition, first release and build order), **Decisions for you** (numbered: each open solution choice with 2-3 options, open questions, riskiest assumptions, gap decisions), **Risks**, **Next** (Build).

On approval: each choice in the definition becomes `accepted` (or `rejected`/`deferred`), its `version` becomes `1.0` and `status` `approved`, the reply goes into its `approvals` (gate 2) and the gate file, and `state.json` moves to `build`.
